# From Bloom to Binary Fuse: Why We Replaced a 50-Year-Old Algorithm

Imagine you run a database with 500 million records stored on disk. 

A user asks: *"Does user #849204 exist?"*

Checking your disk or cloud storage to find out a record **doesn't exist** is the slowest thing a computer can do. It's like walking down into a dark library basement to look for a book, only to realize after twenty minutes that the library never owned it.

To prevent those wasted trips, databases put a **filter** in front of the disk in fast RAM:

* If the filter says **"Definitely not here"**, the database rejects the request immediately. No slow disk reads, no wasted CPU.
* If the filter says **"It might be here"**, the database goes to disk to fetch the record.

In **1970**, Burton Bloom invented the **Bloom Filter**. It was a breakthrough: using just a few bits per item, you could protect databases from millions of useless disk reads. For over 40 years, developers treated it like a solved problem.

So why did computer scientists spend the last decade inventing **Cuckoo Filters (2014)**, **XOR Filters (2019)**, and **Binary Fuse Filters (2020)**? 

What was broken with Bloom filters—and why do modern alternatives win?

---

## 1. Bloom Filters (1970): The Classic Pioneer

A Bloom filter is simply a long row of bits, all starting at `0`.

When you insert an item, you run it through several hash functions (say, 3 or 5 of them). Each hash points to a specific slot in the row, and you turn those bits from `0` to `1`.

When someone queries an item, you check those same slots:
* If **any** of the slots is `0`, the item was never inserted. Guaranteed.
* If **all** of them are `1`, the item is probably in the set.

### Why Bloom Filters Started Failing in Modern Systems

If Bloom filters worked so well for decades, why do we need replacements? 

Because as software scale grew, two fatal flaws emerged:

1. **You Cannot Delete Anything (The Ghost Record Problem)**  
   When you insert item $A$, it turns slots 2, 7, and 12 into `1`. Later, item $B$ gets inserted and shares slot 7. If you try to delete item $A$ by flipping slot 7 back to `0`, you just secretly destroyed item $B$!  
   Because bits are shared, **deletions are impossible**. In systems where users delete accounts, sessions expire, or cache keys change, a Bloom filter slowly fills up with leftover `1`s. Over time, it starts answering "Maybe" to almost every query, rendering it useless.

2. **It Stalls Modern CPUs (The Cache Miss Problem)**  
   Computers in 1970 had uniform memory speeds. Modern computers don't: CPUs are blindingly fast, but reading from main RAM is painfully slow. Modern chips rely on tiny, super-fast L1 and L2 caches.  
   To check one item in a Bloom filter, your CPU has to jump to 5 or 8 completely random locations scattered across megabytes of RAM. That forces the CPU to stall and wait for RAM multiple times for a single check.

## 2. Cuckoo Filters (2014): Solving the Deletion Problem

In 2014, researchers asked a simple question: *What if, instead of scattering single bits all over memory, we stored compact item "fingerprints" in small, organized buckets?*

Enter the **Cuckoo Filter**.

Instead of a raw bit array, a Cuckoo filter is an array of buckets, and each bucket holds small fingerprints (like a 1-byte identity tag). Each item only has **two possible buckets** it can ever live in ($b_1$ and $b_2$), calculated with a clever math trick called *partial-key cuckoo hashing*:

```text
bucket_1 = hash(x)
bucket_2 = bucket_1 ⊕ hash(fingerprint(x))
```

### Why Cuckoo Filters Win:

* **Instant $O(1)$ Deletions**: Want to delete an item? Calculate its fingerprint and inspect its two candidate buckets. If you find the fingerprint, wipe that one slot. Done! It doesn't break any other key.
* **Way Better Cache Locality**: Instead of jumping to 7 random memory addresses across RAM, the CPU only checks **two contiguous buckets**. That means at most 2 memory reads—dramatically reducing CPU stalls.
* **Less Memory**: For false-positive rates below 3%, Cuckoo filters actually use fewer bits per item than a Bloom filter.

**Where to use it**: Any live, active system where records are updated, invalidated, or deleted (e.g. user sessions, network routers, shopping carts, live caches).

---

## 3. The Static Data Revelation: Do We Even Need Dynamic Inserts?

Cuckoo filters solved deletions for live workloads. But around 2018, database architects at RocksDB and Cassandra noticed a different pattern:

In modern LSM-tree storage engines, database files (called SSTables) are **immutable**. Once written to disk, they are never edited—only read millions of times, and eventually deleted wholesale during compaction.

If your dataset is fixed and never receives one-by-one inserts, why pay the memory overhead of dynamic bucket collision tables?

That realization gave birth to the **static filter revolution**.

---

## 4. XOR Filters (2019): The Speed Champion for Read-Only Data

In 2019, Daniel Lemire and Martin Dietzfelbinger created the **XOR Filter**.

Instead of hash tables or buckets, XOR filters treat filter lookup as a simple arithmetic equation:

```text
Block_0[h0(x)] ⊕ Block_1[h1(x)] ⊕ Block_2[h2(x)] == fingerprint(x)
```

During construction, the filter analyzes the entire batch of keys and solves an assignment puzzle so that when you XOR the values from three specific positions, you get the item's fingerprint.

/>

### Why XOR Filters Win:

* **Zero Guessing, Exactly 3 Memory Reads**: The lookup has no loops, no bucket collisions, and no branching. The CPU fetches three spots, XORs them together, and checks the fingerprint in ~12 nanoseconds.
* **20% Smaller Than Bloom**: For the same 1% error rate, a Bloom filter needs ~10 bits per item. An XOR filter needs only **~9.8 bits**.
* **The Trade-off**: You must build it all at once from a batch of keys. You cannot add new items to an existing XOR filter on the fly.

---

## 5. Binary Fuse Filters (2020): Squeezing Space to the Mathematical Limit

While XOR filters were blazing fast, they had one flaw: dividing the array into three separate disjoint blocks left about ~23% of empty slack space during construction.

In 2020, Thomas Mueller Graf and Daniel Lemire fixed this with **Binary Fuse Filters**.

Instead of three isolated blocks, Binary Fuse filters use **overlapping, sliding segment windows** (like shingles on a roof). Keys in adjacent regions share boundary slots.

<Figure
  src="/writing/binary-fuse-filter.svg"
  alt="Binary Fuse Filter (2020) Overlapping Sliding Windows and Optimal Bound"
  caption="FIG 4.0 — Binary Fuse Filter: Sliding segment windows eliminate wasted capacity, reaching ~1.12 bits/key near the theoretical limit."
/>

### Why Binary Fuse Filters Win:

* **Near-Theoretical Space Limit**: Information theory proves you cannot compress membership testing below $\approx 1.12 \times \log_2(1/\epsilon)$ bits per key. Binary Fuse filters get within ~12% of that mathematical ceiling—using just **~8.9 bits per item** at 1% error rate.
* **Builds 2x Faster**: Because overlapping windows make the solver's job easier, construction finishes in strict linear time ($O(N)$) and uses very little temporary RAM.
* **Clustered Memory Reads**: The three lookups happen inside a localized sliding window, preserving CPU cache lines.

Today, Binary Fuse filters are the state-of-the-art choice for read-heavy immutable tables in modern analytic and storage engines.

## Summary: Which Filter Should You Actually Use?

| Feature | Bloom Filter (1970) | Cuckoo Filter (2014) | XOR Filter (2019) | Binary Fuse Filter (2020) |
| :--- | :--- | :--- | :--- | :--- |
| **Can you delete items?** | ❌ No | ✅ **Yes ($O(1)$)** | ❌ No (Static) | ❌ No (Static) |
| **Can you add items on the fly?** | ✅ Yes | ✅ Yes (Until full) | ❌ No (Batch build) | ❌ No (Batch build) |
| **Bits needed per item (at 1% error)** | ~10.0 bits | ~8.4 – 9.0 bits | ~9.8 bits | **~8.9 bits (Smallest)** |
| **CPU memory stalls per check** | High (5–8 random seeks) | Low (at most 2 buckets) | Fixed (exactly 3 reads) | Fixed (3 clustered reads) |
| **Best suited for** | Legacy apps / append-only logs | Live caches, expiring sessions | Static read indexes | RocksDB SSTables, static datasets |

---

### The Plain-English Rule of Thumb

1. **Need live updates and deletions?**  
   Use a **Cuckoo Filter**. It gives you clean $O(1)$ deletions and only checks 2 cache lines, avoiding the memory-destroying flaws of Bloom filters.
2. **Have static, read-only data?**  
   Use a **Binary Fuse Filter**. It is constructed once in milliseconds, takes up the least memory physically possible (~8.9 bits/key), and evaluates queries in nanoseconds.
3. **Only handling streaming append-only logs where items are never removed?**  
   A classic **Bloom Filter** is still acceptable, but understand that your CPU is paying a cache-miss penalty on every query.
